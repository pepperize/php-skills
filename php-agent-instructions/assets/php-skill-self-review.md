## PHP Skill Self Review

After making PHP code, test, or skill changes, review staged and unstaged diffs and task-created untracked files before the final response. Use `git status --short` to include new files that `git diff` omits.

- Treat relevant PHP skills as active decision guides, not background reading.
- Before editing, name the applicable skills and the exact rules that constrain naming, exceptions, logging, validation, authentication, authorization, testing, migrations, and architecture.
- Use `php-domain-clarification` before coding when domain rules, identifiers, persistence shape, scoping, or externally visible behavior are unclear.
- Use `php-solid-review` for explicit code, architecture, and design reviews and to self-review non-trivial implementations against the engineering principles that materially apply.
- Use `php-readable-code` for naming, guard clauses, factories, utilities, and readability.
- Before choosing a new class name or renaming a class, identify its primary responsibility and apply the matching `php-readable-code` naming rule.
- Before finalizing, inspect every new or renamed class and every class whose responsibility changed. Determine its role from the implementation and correct naming mismatches throughout the affected code, tests and documentation. Briefly report the role, returned product (if any), and naming decision for newly introduced collaborators.
- When implementing or refactoring REST resource endpoints, apply `php-api-endpoints` and read its worked User endpoint reference before editing. Follow the default Controller -> Service -> Repository flow, with an optional Client behind the repository: services use input/output DTOs, repositories use entities, and factories construct entities from input DTOs and output DTOs from entities. Apply the matching role suffixes from `php-readable-code` and explain concrete departures. Preserve attribute-based input validation, direct Doctrine entity mapping when Doctrine is in use, and explicit project architecture and mapping policies.
- Distinguish REST resource endpoints from server-rendered pages and traditional HTML form actions. For REST, keep the resource name through controller, service, and DTOs and use supported `create`, `read`, `update`, and `delete` service operations, such as `UserService::create()`. A completed resource-creation POST requires the service to map the persisted entity to a public resource DTO, such as output-only `UserDto`, and the controller to delegate that DTO to the response collaborator for `201`, its member `Location`, and a representation including its identifier without secrets. Read the HTTP endpoint examples in `php-readable-code`. Keep ViewService/Renderer patterns for HTML pages and capability services plus HTML errors/success redirects for explicitly required traditional form posts; a server-rendered form calling a REST resource endpoint follows REST rules.
- Before finalizing, verify that every new or renamed injected dependency and its test collaborators use the complete declared short type in lower camel case, never a plural resource alias.
- Use `php-templating` for server-rendered controllers, page templates, partials, localized email bodies, and template-input changes.
- Use `php-testing-style` for all test naming, mocks, unit/integration boundaries, assertions, layout, and verification scope.
- Use `php-application-security` for input validation, regex safety, and other application-security-sensitive code paths.
- Use `php-request-validation` for request DTO hydration, Symfony constraints, validation middleware, typed controller argument delivery, Problem Details, and browser submission handling. In Slim, prefer validated DTO parameters resolved by declared type from class-keyed request attributes; verify missing or wrongly typed required DTOs raise `LogicException` at the invocation boundary before name-based or container fallback, and keep submitted DTOs out of the shared container. Default forms to JavaScript-managed submissions that validate locally before sending, preserve inputs, and own displayed messages and localization. Interpret actionable server types or codes with frontend-owned feedback; never display server diagnostic text, and use a local generic summary for unknown or unmapped failures. Ordinary HTML submission flows require an explicit project or task requirement.
- Shape immutable input DTOs as application service input. By default, pass the same validated DTO instance from the controller directly to a typed service parameter. Symfony constraint attributes are permitted metadata on shared application input DTOs; validator execution and violation handling stay at the input boundary. Before finalizing, verify that any separate service input type and mapping address an actual difference in contracts, rather than architectural roles, names, or hypothetical callers.
- Within the backend, validate external input only in the input layer; this does not prohibit independent browser validation. In typical PHP HTTP applications, declare constraints as attributes on the input DTO and execute them in route middleware. Hydrate and perform permitted normalization once at the input boundary. Controllers, services, command/domain constructors, repositories, and output code must not repeat field validation or input normalization; other external entry points validate at their own input boundary. State-dependent business decisions stay in their owning operation.
- For regex-based fields, use one full-value regex per field, preferably sharing the canonical body with frontend HTML5 `pattern`; do not stack separate character-rule regexes. Validate at input and escape or encode at the final output context, preserving original DTO and stored values.
- Use `php-authentication-security` when adding, changing, or reviewing login, credentials, password policy or hashing, sessions, logout, account recovery or verification, authentication throttling, or MFA.
- Use `php-rbac-authorization` when adding, changing, or reviewing roles, permissions, authorization attributes, protected routes or controllers, object-scoped access, or RBAC mappings.
- Use `php-logging-exceptions` and `php-database-migrations` when changes touch those areas.
- Use `php-shared-hosting-deployment` for deployment work only when root `AGENTS.md` contains the shared-hosting activation marker and exactly one supported database marker. Select only that SQLite or MariaDB example; absent or conflicting markers keep the skill inactive.
- Use `php-clean-architecture` and `php-ddd-architecture` only when this project's instructions explicitly state those architectures.
- Before finalizing, review new or changed helper methods with `php-readable-code`.
- Before finalizing, review thrown/caught exceptions and logging decisions with `php-logging-exceptions`.
- During design review, name the applicable principle in each meaningful finding. Do not emit a principle checklist, manufacture violations, or recommend speculative abstractions.
- A design self-review may conclude that no relevant principle violation was found.
- Before finalizing a server-rendered page, verify that it receives one typed page ViewModel, structured nested values use ViewModels, and render arrays exist only as template-engine adapters.
- Before finalizing a localized email body, verify that each distinct outcome and supported locale has one complete template, long-form prose is absent from translation catalogs and line assembly, rendering does not apply a page layout, and real-renderer tests cover each combination. When multiple email families share a locale-qualified filename convention, verify that template-path construction and locale context use a shared application renderer with closed template and locale types.
- Do not add defensive branches unless the domain/API path can actually produce that state.
- Fix meaningful issues found during self-review before finalizing.
- Keep cleanup scoped to the requested change.
